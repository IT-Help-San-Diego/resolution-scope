## 3. QEMU runtime finding — RESOLVED (2026-08-22)

The GIC data abort was a **wrong QEMU invocation**, not a kernel defect. The
Microkit manual (`doc/microkit_user_manual.pdf` §8.13 "QEMU virt (AArch64)")
gives the canonical command, which differs from the obvious `-kernel` form in
two load-bearing ways:

1. The image is loaded via `-device loader,file=<img>,addr=0x70000000,cpu-num=0`
   (NOT `-kernel`). `-kernel` places the image at a different address and the
   kernel's GIC mapping lands wrong → the `KERNEL DATA ABORT` at the GIC.
2. `-m size=2G` — the board is built for **2GB** main memory (the
   `platform_gen.json` "memory" entry of 0x60000000..0xc0000000 is the kernel's
   *available* region, NOT the QEMU memory size; reading it as "1.5GiB" and
   passing `-m 1536` was a red herring).

Canonical command (verbatim from the manual):

```
qemu-system-aarch64 \
    -machine virt,virtualization=on \
    -cpu cortex-a53 \
    -nographic \
    -serial mon:stdio \
    -device loader,file=[SYSTEM IMAGE],addr=0x70000000,cpu-num=0 \
    -m size=2G
```

**Verified result** — the hello example boots and prints:

```
Booting all finished, dropped to user space
INFO  [sel4_capdl_initializer::initialize] Starting CapDL initializer
MON|INFO: Microkit Monitor started!
hello, world
```

The `"Could not infer GIC interrupt target ID, assuming 0"` warning is benign
(it appears in successful boots too; it is seL4's GICv2 target-id inference
logging, not the fault source). The whole seL4 → CapDL → Microkit → PD chain is
now proven running on the Beelink.
